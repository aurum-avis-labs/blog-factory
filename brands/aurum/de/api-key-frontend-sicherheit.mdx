<p class="blog-lede">API Key Frontend Sicherheit heisst: alles, was im JavaScript-Bundle landet, ist öffentlich. Erlaubt sind bewusst publishable Schlüssel (Stripe Publishable Key, Supabase Anon Key). Verboten sind Service-Role-Keys, OpenAI-Tokens und Passwörter, auch wenn ein KI-Assistent sie in eine «öffentliche» Umgebungsvariable geschrieben hat.</p>

## API Key Frontend Sicherheit prüfen

Wer mit Lovable, Bolt, v0, Replit oder Cursor gebaut hat, sollte den Export behandeln wie eine veröffentlichte Webseite: Mindestens URL und oft ein Supabase Anon Key stecken im Client. Das ist kein Skandal, solange Row Level Security die Daten trennt. Der typische Unfall ist ein Service-Role-Key oder ein bezahlter API-Token in `VITE_`- oder `NEXT_PUBLIC_`-Variablen. Die RLS-Seite dazu: [Lovable Supabase RLS](/de/blog/lovable-supabase-rls).

<ol class="blog-steps">
  <li data-step="1"><h3>Repository und gebautes Bundle durchsuchen</h3><p>Nach key, secret, token, service_role, sk- und Ihren Anbieter-Namen suchen. Das Produktions-JavaScript in den DevTools unter Quellen öffnen und erneut suchen.</p></li>
  <li data-step="2"><h3>Jeden Treffer einordnen</h3><p>Öffentlich by design (Stripe Publishable Key, Supabase Anon Key) gegen nie client-seitig (Service Role, OpenAI, Webhook-Signing-Secrets).</p></li>
  <li data-step="3"><h3>Alles Rotierte neu ausstellen, was exponiert war</h3><p>Keys, die je im Frontend oder in einem öffentlichen Repo lagen, gelten als verbrannt. Neue Keys im Dashboard ausstellen, dann erneut deployen.</p></li>
  <li data-step="4"><h3>Privilegierte Aufrufe hinter das eigene Backend ziehen</h3><p>Server-Routen, Edge Functions oder eine kleine API, die Sie kontrollieren, halten den sensiblen Key und prüfen, wer was darf.</p></li>
</ol>

## Was im Frontend bleiben darf

Der Supabase Anon Key ist für Client-Apps gedacht. Er ersetzt keine Zugriffskontrolle: Policies entscheiden, welche Zeilen ein anonymer oder eingeloggter Nutzer sieht. Stripe unterscheidet publishable und secret; nur der publishable Teil gehört in die Oberfläche.

Vite liefert Variablen mit Prefix `VITE_` an den Browser. Next.js macht das mit `NEXT_PUBLIC_`. Ein OpenAI-Key dort landet im öffentlichen Bundle. Fremde können damit auf Ihr Guthaben zugreifen. KI-Tools schlagen das manchmal vor, weil die Demo sofort läuft.

## Was nie ins Bundle gehört

Der Supabase Service-Role-Key umgeht RLS. Webhook-Signing-Secrets, Datenbank-URLs mit Passwort und Admin-Tokens gehören auf einen Server, den Sie kontrollieren, nicht in GitHub und nicht in die Hosting-Konsole als «public env». `.env` auf dem Laptop schützt nicht, wenn die Datei mitgeschickt oder fotografiert wird.

Logs und Fehlermeldungen leaken ebenfalls: wer Requests mit vollem Header loggt, exportiert Schlüssel in Monitoring-Tools. Ausgangspunkt: das Bundle ist öffentlich.

Privilegierte Aktionen gehören hinter eine Route, die Sie kontrollieren: Supabase Edge Functions, ein kleines NestJS- oder Node-Backend, oder serverseitige Hooks Ihres Hosters. Der Browser ruft nur Ihre URL auf; der Server hält den Service Key und prüft Session oder Rolle. KI-Generatoren legen solche Schichten nicht immer an, wenn die Demo «nur» Daten anlegt. Für einen Pilot mit echten Kundendaten ist das der Unterschied zwischen sichtbarem Anon Key und offenem Datenbankzugriff.

Nach einer Rotation: alte Keys in Dashboards deaktivieren, CI und Hosting-Variablen aktualisieren, einen Build auslösen und erneut im Bundle suchen. Einmal reicht nicht, wenn drei Umgebungen dieselbe Datei kopieren.

## Ein erfundenes Beispiel: der Launch am Freitag

Ein erfundenes Beispiel: eine Person in Zürich veröffentlicht nach Lovable eine Beta für Team-Aufgaben. In der Readme stehen `VITE_SUPABASE_URL` und `VITE_SUPABASE_ANON_KEY`, korrekt. Zusätzlich liegt `VITE_SUPABASE_SERVICE_KEY` aus einer Seed-Phase im selben Block. Vor dem Freitag-Post prüft niemand das Build-Artefakt. Ein Besucher kopiert den Service Key aus den DevTools und liest die Tabelle `profiles` ohne Login. Die Person rotiert den Service Role in Supabase, verschiebt Admin-Aufgaben in ein Skript lokal und testet neue Policies ausgeloggt im Netzwerk-Tab. Der Anon Key bleibt im Client.

Das stoppt den akuten Leak. Es beweist nicht Compliance, noch dass Fremde keine fremden Datensätze per ID erraten können.

## Was die Prüfung beweist und was nicht

Kein Service Role im Bundle bedeutet: eine grosse Fehlerklasse ist weg. Es bedeutet nicht, dass RLS vollständig ist, Uploads privat sind oder jede Route den Aufrufer prüft. Viele öffentliche Meldungen zu Lovable und Supabase betreffen Policies, nicht «geheime» Anon Keys.

Wenn Sie Authorization testen wollen, loggen Sie sich aus und versuchen Sie fremde IDs in URL oder API-Aufruf. Das schliesst eher an [Ist Ihre vibe-coded App produktionsreif](/de/blog/ist-deine-vibe-coded-app-produktionsreif) an als jede reine Schlüsselsuche. Wer noch an der ersten Lovable-Sequenz hängt, findet den Ablauf in [Lovable MVP](/de/blog/lovable-mvp); beides ersetzt keine Review, wenn der Code schon extern geteilt wird.

<div class="blog-faq">
  <h3>Ist der Supabase Anon Key ein Geheimnis?</h3>
  <p>Nein. Er ist publishable. Schutz kommt von RLS und serverseitiger Logik, nicht vom Verstecken des Strings.</p>
</div>

<div class="blog-faq">
  <h3>Reicht es, Secrets nur in .env zu lassen?</h3>
  <p>Nur wenn diese Datei nie im Repo, nie im Client-Build und nie als «public» im Hosting landet. Alles mit VITE_ oder NEXT_PUBLIC_ wird gebündelt.</p>
</div>

## Wann ein Vibe Code Review passt

Ein [Vibe Code Review](/de/services/vibe-code-review) passt, wenn das KI-Repo die Basis für Investoren, eine Sicherheitsfrage im Unternehmen oder erste zahlende B2B-Kunden ist und Sie eine strukturierte Lücke gegen OWASP ASVS v5.0 wollen statt weiterer manueller Suche. Dazu kommen priorisierte Massnahmen, fokussierte Zeit für Architektur und Codequalität sowie ein abschliessendes Gespräch unter NDA.

Solange die Idee noch wöchentlich kippt, reichen offensichtliche Rotationen; buchen Sie die Review, wenn der Stand stabil genug ist, um ihn zu schützen.
