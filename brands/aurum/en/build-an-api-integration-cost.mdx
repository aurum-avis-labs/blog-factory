## What it costs to have an API built

"Asking someone to build an API" sounds like one price tag. In practice you pay for a recurring handoff between two systems you already use. In our fixed-price packages, the figures below are **guide ranges** (final numbers in the conversation): Small about 2–3 days, Medium about 7 days, Large about 10 days, Max from about 12 days. Hosting afterwards is typically CHF 50–150 a month, plus platform or AI use the job actually needs. There is no flat "per integration" fee, because fields, directions and failure paths change the work.

The wider picture of deposit, acceptance and operations is in [what automation costs in Switzerland](/prozess-check/blog/what-automation-costs-switzerland). This page stays on the pipe: system A hands data to system B so a colleague stops retyping the same fields.

If you cannot name the two systems yet, you are not in a band. You need a description of the task first, not a quote.

## When a connector is enough

A connector is enough when both sides sit in a product with a ready link and the job is "when event X happens, write these fields there". Microsoft lists more than 1,000 connectors for Logic Apps, Power Automate, Power Apps and Copilot Studio. You pay for configuration and someone who reads failure mails, not a new program on your own server.

A custom connector, in Microsoft's wording, wraps a REST or SOAP API for a service outside that list. You still need credentials and a description of the operations. That is less than bespoke code, more than ticking a standard connector.

We have connected Microsoft 365 (Graph, Outlook, Bookings, Teams), Google Workspace and Stripe. We have not built a ready link to bexio, Abacus or a trade package. If the vendor has an API, that is on their side, and it must be checked against your account.

If the "system" is an Access file on a drive, there may be nothing to call. Start with [whether to replace that Access database](/prozess-check/blog/replace-access-database). A file does not become an API because someone books development.

## What the build days are for

The days are not an empty shell around "coding".

<ol class="blog-steps">
  <li data-step="1"><h3>Name the task</h3><p>One handoff, the fields, and which system wins if both have a value.</p></li>
  <li data-step="2"><h3>Check access</h3><p>Documented API, test account, permission that is not a shared admin login.</p></li>
  <li data-step="3"><h3>Build the success path</h3><p>One record crosses. You can point at it in both systems.</p></li>
  <li data-step="4"><h3>Build the failure paths</h3><p>Duplicate, missing field, timeout. Each outcome is written down.</p></li>
  <li data-step="5"><h3>Tell and hold</h3><p>Who gets the mail, and where a failed record waits until someone touches it.</p></li>
</ol>

Small is those five steps on a narrow handoff. The guide range rises when step 2 means a week waiting on the vendor, or step 4 has many variants because the data is dirty. Calendar waiting is not the same as build days. A quote that hides waiting looks cheap and finishes late.

How to tell whether the person across the table can do this, and will still answer afterwards, is in [choosing an automation partner](/prozess-check/blog/choosing-an-automation-partner).

## A made-up example

A made-up example: a facilities firm of 20 people closes a job in a planning tool. A colleague retypes eight fields into the invoicing tool, about twelve times a week, ten minutes each. The service date is wrong often enough that the invoice bounces. Both tools are cloud products with a documented API and a test account. Failures should land as a mail to one person, with the job number.

That shape sits in the Small guide range (2–3 days, CHF 3'200–4'800) if the test account works in the first sitting and the eight fields exist on both sides under clear names. It drifts toward Medium if the invoicing tool needs three related records first and one list is free text in the planning tool. It is not an integration project if the invoicing "tool" is Access with no API. The firm, frequency and minutes are invented so the band has a shape. Your fields decide.

## What should not sit in the same guide range

Do not fold a customer portal, a redesigned status process and "while you are there, the reports" into the same fixed price. The interface is the pipe. Portal, status model and monthly report are neighbouring jobs. Price them when they are written down.

Do not promise the vendor API will stay still. Vendors change fields. The build should fail loudly when a field disappears. That is step 4, not a guarantee in the day rate.

Excel between two systems with no interface is often the honest interim. A built handoff pays off when someone maintains the sheet every week, duplicates appear, or numbers must reach accounting before the file is trustworthy. Then frequency and error cost matter, not the wish to "finally have an API".

## Short questions

### Is Zapier or Make enough on its own?

Often for a simple one-way copy between two cloud tools with an official connector. Once permissions, tenant separation or failure handling need documenting for your firm, it becomes a project with the five steps above, not just a new subscription.

### Who should not expect a fixed price yet?

When the vendor only opens the API "on request", when contract or legal terms are still open, or when you are still introducing the target system. The next step is clarification, not Small.
