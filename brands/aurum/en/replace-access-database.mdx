## Replace an old Microsoft Access database, or keep it

<p class="blog-lede">Replacing an Access database pays off when more than a few people depend on one file, the only person who can change it is leaving, or the edition you run will no longer receive security updates.</p>

Keep the file when a handful of people use it, that edition is still in support, a second copy exists somewhere, and a new system would cost more than the risk you can name. The October 2026 date is not an order to rebuild. It is a reason to look up which Access is actually installed.

An Excel workbook that has quietly become the real system is a different topic, covered in [Excel as a shadow system](/prozess-check/blog/excel-as-shadow-system). This page is the .accdb: tables, forms, reports, and usually one person who knows how they fit.

In short: replace when several people share one file, only one person can change forms or fields, or the machine runs Access 2021 or LTSC 2021 with no planned edition change. Keep it when a few users share one file, the edition is still in support, a tested backup exists, and the pain is copying, not the platform.

## Which support date applies to your edition

Microsoft lists Access 2021 and Access LTSC 2021 for 13 October 2026 among products whose support ends. On that list, end of support means no new security updates, no non-security updates, no assisted support, and no online technical content updates. The product page for Access 2021 also shows 14 October 2026, 6:59:59 am Pacific. Use the edition on the machine, not a blog summary of "Access".

Access 2024 is a different product. Its lifecycle page shows retirement on 9 October 2029. Desktop database files (.accdb) were not shut down when Access web apps left SharePoint Online. Microsoft stopped new web apps in June 2017 and shut the remaining ones down by April 2018, and said it would keep investing in Access desktop databases. A file on a PC is not that retired web feature.

If the title bar says Microsoft 365, do not assume the 2021 date. An unsupported program can keep running. It just stops receiving fixes.

## Five paths off the file

| Path | Fits when | Walk away when |
| --- | --- | --- |
| Keep Access | Few people, one file, edition still supported, a second copy exists | Several people share one file, or the form owner is about to leave |
| SharePoint Lists | One table, simple columns, the team already lives in Microsoft 365 | Many related tables, forms and reports must survive |
| Dataverse | You want tables in Microsoft's cloud data platform, Access can stay as the screen for now | Every column type must move unchanged, or nobody will pay for the platform afterwards |
| A standard program | The file is really invoices, stock or a CRM, and a product already sells that | The steps are office-specific and a package would bend the work |
| A small app | The steps are specific, the data is yours, and the other rows do not fit | The forms are not described yet |

Microsoft's current migration document is about Dataverse. Access can export data to Dataverse or Dataverse for Teams. Not every Access data type is supported, and limits differ. Afterwards the tables can sit outside the file while the desktop client remains the screen. That is a move of the data, not an automatic copy of every form, report and macro. If required fields and statuses live only in a form or in one person's head, the new store will not have them until someone writes them down. Test on a copy. Compare row counts. Anything the tool refuses stays in Access.

Lists fits when the "database" is one table, such as an equipment register. It does not fit when the value sits in five linked tables and a form someone spent years adjusting.

A standard program wins when you would rebuild invoicing or stock software that already exists. A small app wins when the form encodes a sequence no package matches. ## The risk already in the file

The usual Access risk is a shared file, not a missing licence.

Several people open the same .accdb on a drive. Access locks records, the file grows, and "final" sits beside "final2". The form owner is the only one who can add a field. If that person is ill, the office keeps typing into a tool nobody else can repair. Anyone who can open the folder can copy the whole database. A server database with accounts does not behave like that.

<ul>
  <li>Restore yesterday's backup on another PC and open the form</li>
  <li>Note a row count per table from the copy before you promise a date</li>
  <li>Record the edition in the title bar and accept or plan around end of support</li>
</ul>

End of support in 2026 applies only to the editions on the list. Newly found problems in that edition will not be patched. If the file never leaves the office and the PC is current, some firms accept that for a while. Write the acceptance down.

## A made-up example

A made-up example: an installer's office of 15 people has tracked service jobs in Access since 2014. One coordinator built the forms. Four people enter jobs. The file sits on a shared drive. The title bar is Access 2021. There is a copy on the coordinator's laptop from March, never opened.

They should not start by commissioning an app. They should open the March copy on another machine and confirm the jobs are there. Then count what the file really is. If jobs, parts and invoices are tangled, a stock program and a small app might be two separate decisions. If it is one list of open jobs with a few columns, Lists is a candidate. If the coordinator is staying and four people is still tolerable, they can stay on Access until the edition changes or the role changes.

What they should not do is import the tables over a weekend and call the forms done. The form hides required fields and allowed status names. Those rules belong next to the table before the office leaves the file.

The firm, year and headcount are invented. Your file decides the row in the table.

## What a move has to include

Name live tables and history. Export a row count per table from the copy. List columns the migration tool will not take, from Microsoft's type notes, before you promise a date. Decide whether Access remains the screen for a while. That is a bridge, not a permanent stop, if the reason you moved was that only one person could change the screen.

Then decide who can see which rows. A file has no accounts. The new store should not give everyone the full history because that was how the drive worked.

Guide prices for a bounded build are in [what automation costs in Switzerland](/prozess-check/blog/what-automation-costs-switzerland). They are not a flat quote for "replace Access". The size is the workflow you can point at after the forms are described.

Before you ask for a quote, spend half an hour clicking through a typical form and writing down required fields. That is not IT work. It saves weeks in the project.
