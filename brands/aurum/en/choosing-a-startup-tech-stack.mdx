<p class="blog-lede">Choosing a startup tech stack means deciding which layer of the product must be real for the hypothesis you are running now: the browser surface, the API and database, auth, and where it runs. The right stack is the one that lets you learn in weeks without locking you into the wrong data shape or the wrong security model for the next phase.</p>

You already have an export from Lovable, Bolt, v0, Replit, Cursor, or Claude Code. The stack question is not "React or something else on a slide". It is whether the defaults your tool chose still match the job once strangers use the product. For why measurement and deployment quality matter alongside stack choice, see [why we build production-quality MVPs](/blog/why-we-build-production-quality-mvps). For client shape (browser, store, wrap), see [how to build a scalable MVP](/blog/how-to-build-a-scalable-mvp) and web app vs native app vs PWA.

## Choosing a startup tech stack

Treat the stack as four decisions you can name in a meeting, not a shopping list of fashionable names.

<ol class="blog-flow">
  <li><strong>Surface</strong><p>Mobile web, desktop web, native shell, or wrapped web. Store rules and offline needs follow from here.</p></li>
  <li><strong>Data</strong><p>Relational rows, documents, files, or mostly events. Changing this later is a rewrite, not a migration toggle.</p></li>
  <li><strong>Auth and permissions</strong><p>Who can read and write which records. UI hiding a button is not authorization.</p></li>
  <li><strong>Hosting and ops</strong><p>Region, backups, secrets, and who gets paged when something breaks on a Sunday.</p></li>
</ol>

The vibe-coding path often lands on a React front end with a hosted Postgres (for example Supabase) because the tools wire it quickly. That is a serious way to learn. So is a custom API on a cloud you control. So is staying in the browser until you know the job is worth a store submission. None of those choices, alone, proves demand.

## Decisions that cost you later

**Data model first.** If your MVP is orders, memberships, invoices, or multi-step forms with relationships, a relational database and SQL usually match how you already think. If the prototype is feeds, presence, or chat-shaped threads, document stores and realtime SDKs can be faster. Pick the shape that matches the behaviour you are testing, and accept that a pivot may include moving data.

**Auth where the data lives.** Backend-as-a-service stacks put policies next to the database: row level security on Postgres, security rules on Firestore. Generated policies from a tool are a draft. [CVE-2025-48757](https://nvd.nist.gov/vuln/detail/CVE-2025-48757) documented missing or ineffective RLS on many Lovable-linked Supabase projects, where the public client key could query without login. Your stack is not safe because the demo works while logged in as yourself.

**Hosting and Swiss questions.** If partners ask where data sits, Supabase lets you select region Zurich (eu-central-2) at project creation ([region docs](https://supabase.com/docs/guides/platform/regions)). Other hosts follow their own region lists; confirm in the console instead of guessing in a pitch deck. Location does not replace access control or contracts under the Swiss FADP.

**Code you can keep.** Employee-written software belongs to the employer under Swiss law ([Art. 17 URG](https://www.rentschpartner.ch/ict-law/schutz-von-software)); work from an external author stays with the author until assignment. For a startup, "we own the repo" should be explicit in writing before you fund the next build. The stack should not trap you in a host you cannot export from.

## One production path among many

The product validation package Aurum sells deploys on **Azure with React and NestJS** because many founders eventually need a measured build, code they own, and room to pivot without fighting a no-code ceiling. That is one honest stack for twelve weeks of validation, not the only stack a Swiss startup may choose. Teams ship learning products on Supabase, Firebase, Rails, .NET, or mobile-native code every day. The mistake is treating a blog’s favourite triangle as destiny, or treating a vibe-coded export as finished architecture without a plan.

Ideas as such are not protectable in Switzerland ([IGE](https://www.ige.ch/de/uebersicht-geistiges-eigentum/ein-leitfaden-fuer-innovative-und-kreative/idee/koennen-ideen-geschuetzt-werden)). The stack does not hide the concept. It only affects how fast you read behaviour and how painful the next layer is.

## What the stack choice does not prove

A coherent stack lets you instrument signups, sessions, drop-off, and support load. It does **not** prove pricing power, marketplace liquidity, or that your wrapped web app will pass [App Store guideline 4.2](https://developer.apple.com/app-store/review/guidelines/) or [Google Play closed testing rules](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en) when you add a store build. Those are parallel decisions, not automatic upgrades from "we picked Postgres".

## Who should not spend a week comparing frameworks

If you have not spoken to five people in the target role and the product is still a landing page, pick the default your tool exports and measure. If regulated health data or strict tenant isolation is already in scope, you need architecture help, not another comparison table. If the team argues about lint rules while nobody uses the app, the stack is a distraction.

<div class="blog-faq">
  <h3>Should founders optimise for hiring?</h3>
  <p>Only after the learning goal is clear. A popular framework helps recruiting later; it does not validate the idea. For the first test, optimise for speed to instrumented behaviour and honest limits.</p>
</div>

<div class="blog-faq">
  <h3>Is "scalable" a stack property?</h3>
  <p>Partly. Scale is also product scope, queries, and ops discipline. A small team on a boring monolith often outlearns a microservice diagram nobody operates. Scalability for an MVP usually means "can we change our mind without a six-month rewrite", not "handles a million users tomorrow".</p>
</div>
