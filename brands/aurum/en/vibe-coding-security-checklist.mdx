## Vibe coding security checklist

A **vibe coding security checklist** is a short pass you run on an app you built with Lovable, Bolt, v0, Replit, Cursor, or Claude Code before strangers log in, before you store payment details, or before a pilot customer asks for a security questionnaire. You are not trying to win a certification. You are looking for gaps that AI-assisted builders often leave open: keys in the client, database rules that look fine in the dashboard but fail in practice, and admin screens that anyone with a URL can open.

The list below is neutral about tools. They are excellent for speed. Speed does not remove your responsibility for access control, data location, and recovery. For load, monitoring, and deploy discipline, pair this pass with [is your vibe-coded app production-ready](/blog/is-your-vibe-coded-app-production-ready).

## What this pass does and does not prove

Finishing the checklist means you found and fixed obvious holes, or you wrote down known risks before you ship. It does not mean OWASP ASVS is satisfied, that you pass a penetration test, or that legal review is done. It does not replace a data processing agreement with your host or a privacy notice on your site.

## The checklist (same day)

Work through the items in order. If an item is "not applicable", write why in one line so a future you or a contractor does not assume you skipped it by mistake.

<ul class="blog-checklist">
  <li><strong>Inventory surfaces.</strong> List every way data gets in or out: web UI, mobile wrap, serverless functions, webhooks, email triggers, and any "admin" URL you bookmarked during development.</li>
  <li><strong>Secrets stay server-side.</strong> Search the repo and the built client bundle for service role keys, signing secrets, and third-party tokens. Nothing that can read another user’s row belongs in front-end code or in a public GitHub repo.</li>
  <li><strong>Authentication on every mutating path.</strong> Logging in through the UI is not enough. Call each API route or edge function with no session, with an expired token, and with another user’s token. The unhappy paths should fail closed.</li>
  <li><strong>Authorisation matches the product story.</strong> If only the owner may see a project, prove it with two test accounts. UI hiding is not security. Row level security, policy rules, or server checks must align with what you promise in writing.</li>
  <li><strong>Storage buckets and public links.</strong> Note which buckets are public. Open a "private" file URL in a logged-out browser. Upload paths should not let one user overwrite another's object by guessing an ID.</li>
  <li><strong>Data region and subprocessors.</strong> Write down the region you selected (Supabase offers Zurich, eu-central-2, among others) and every vendor that stores or processes personal data. You will need this for customer questions and for agreements.</li>
  <li><strong>Dependencies.</strong> Run your platform’s audit command on the lockfile you actually deploy. Triage critical findings before you widen access, even if the prototype "worked fine" last week.</li>
  <li><strong>Logging and errors.</strong> Trigger a failure on purpose. Read what lands in logs or client toasts. Stack traces and raw user records in the browser console are a common leak in generated apps.</li>
  <li><strong>Backups and export.</strong> State whether you can restore yesterday’s database and whether a customer can leave with their data. "The platform backs up" is not the same as "we tested a restore".</li>
  <li><strong>Capture the result.</strong> One page: date, who ran the pass, what failed, what you fixed, what remains open. That page is what you hand to the next developer or to a structured review.</li>
</ul>

## A made-up example: a booking tool after the first pilot

A made-up example: a founder ships a room-booking app with Lovable and Supabase for three Zurich co-working spaces. Twelve real members use it. No payments yet, but names, emails, and booking notes are live.

On a Thursday she runs the checklist. The client bundle still contains a commented line with an old anon key from an early experiment; she removes it and rotates keys in the dashboard. Two test accounts show that any logged-in user can open another user’s booking ID by changing the number in the URL; she adds a policy so rows match the member’s organisation ID. A storage bucket marked public serves profile photos; she makes it private and serves images through signed URLs. She notes in her one-page log that backups are "platform default, restore untested" and that error toasts still echo raw SQL on one admin screen she plans to fix before a fourth site joins.

The pass took an afternoon. It did not make the app "bank grade". It stopped an easy cross-tenant read and gave her something honest to send when the next site manager asks what was checked.

## What a structured review adds

When the checklist surfaces several open items, or when a customer asks for evidence against a standard, a structured review beats another evening of guessing. Aurum’s [Vibe Code Review](/services/vibe-code-review) is aimed at apps built with Cursor, Lovable, v0, or Claude Code. Work is mapped to OWASP ASVS v5.0. You receive a gap report, roughly eight hours on architecture and code quality, a prioritised P0/P1/P2 action list, a closing conversation, and an NDA. It fits when you plan to keep the codebase, onboard paying B2B users in Switzerland, or hand the project to an in-house team without losing weeks to archaeology.

If you are still on fake data with five friends testing copy, finish discovery first. Book a review when access control and data location are blocking revenue or a partnership, not when you only need another feature prompt.
