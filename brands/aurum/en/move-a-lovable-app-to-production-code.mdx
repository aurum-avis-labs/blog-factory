## Move a Lovable app to production code

To move a Lovable app to production code you export the generated front end to a repository you control, keep or migrate the Supabase project that holds auth and data, strip secrets from the client, prove row level security under abuse, and deploy the app on hosting you operate. GitHub sync is the usual path; a one-off ZIP works on paid plans if you only need a snapshot. None of that replaces a security review or a later rebuild on a stack your procurement team accepts. This page is for founders and innovation leads who already validated a workflow in Lovable and now owe paying users or a pilot contract something sturdier than a shared preview link.

If you are still asking whether the idea deserves a build at all, stay on [fake door test vs MVP](/blog/fake-door-test-vs-mvp). If investors or a corporate buyer will open the repository, plan for tech due diligence on an AI-built MVP after the basics below.

<ol class="blog-steps">
  <li data-step="1"><h3>Connect GitHub before the codebase forks in your head</h3><p>In Lovable, open Settings → Integrations → GitHub, authorise the app, and link the project. Lovable creates one repository and keeps the default branch in two-way sync. You cannot import an existing repo into Lovable, so treat this as the moment you name the canonical copy.</p></li>
  <li data-step="2"><h3>Clone, install, and run locally</h3><p>Pull the repo, install dependencies, and copy environment variables from Supabase into a local <code>.env</code> file that never gets committed. If the app only runs inside Lovable's editor, fix that before you promise a pilot.</p></li>
  <li data-step="3"><h3>Take inventory of Supabase</h3><p>Note project region, auth providers, tables, storage buckets, edge functions, and every row level policy. Zurich (eu-central-2) is available if you chose it at creation. The database does not live inside the Git export; ownership and billing stay in the Supabase dashboard unless you migrate.</p></li>
  <li data-step="4"><h3>Move secrets off the client</h3><p>Search the repo for API keys, service role keys, and webhook tokens. Anything with admin power belongs on a server you control, not in the browser bundle. The anon key is public by design; policies must enforce who sees which rows.</p></li>
  <li data-step="5"><h3>Test authorization, not only the happy path</h3><p>Script attempts to read another user's rows with a normal session, with no session, and with a tampered user id. Missing or cosmetic row level security has shown up in public incidents on Lovable-style stacks; treat policies as production code.</p></li>
  <li data-step="6"><h3>Deploy the front end outside Lovable</h3><p>Point a static or serverless host at your build output, set production environment variables, wire a custom domain, and turn off reliance on Lovable's publish button for customer traffic. Keep a branch strategy so Lovable edits do not overwrite hardened work without review.</p></li>
</ol>

## What Lovable Code export actually gives you

Export gives you a React-style codebase, version history, and the freedom to run CI, pull requests, and external hosting. Git sync is available on all plans according to Lovable's documentation; downloading the full tree as a ZIP is a paid-plan option when you want a tarball without GitHub.

Export does not give you a second backend, automated tests, clean module boundaries, or proof that strangers cannot read each other's data. It also does not move Supabase: you still log into the same project, or you run a proper migration with downtime and data checks.

## What moving to production code does not prove

A repo on GitHub and a custom domain show you can leave the editor. They do not prove performance at higher load, monitoring when something breaks at night, or that a security questionnaire will pass. They do not replace retention data or a signed pilot.

## A made-up example: from shared preview to pilot host

A made-up example: a two-person team in Bern built a supplier order draft in Lovable for caterers they met at trade fairs. Six chefs tested it; one returned without a reminder. A mid-size firm agreed to a paid pilot if the app runs on the firm's subdomain and a short security memo exists. On Monday they connect GitHub and clone the repo. Tuesday they find a service role key in a committed <code>.env.example</code> and rotate keys in Supabase. Wednesday they write three row level tests and discover draft orders were readable across accounts; they fix policies before Thursday's deploy to a static host. Friday the pilot runs on the new URL; Lovable stays connected for experiments on a branch, not for production traffic. They book a structured review before opening signup beyond the pilot list.

## Who should not rush export

If you have fewer than ten serious sessions and no signal that anyone returns, export is distraction. If your only goal is a slide for a board meeting, a recording of the Lovable preview may suffice until behaviour data exists.

Teams with no one who can read TypeScript and SQL should not equate «we have GitHub» with «we can operate this». Either hire that skill, buy a review, or scope a rebuild.
