<p class="blog-lede">API keys and secrets in AI-built apps belong in two buckets: identifiers meant to be public (publishable payment keys, Supabase anon keys) and credentials that must never ship in the browser bundle (service role keys, OpenAI keys, database passwords). Vibe-coding tools often wire the first bucket correctly and still leave the second in a file that ends up in git or in a Vite build.</p>

## API keys and secrets in AI-built apps

If you built with Lovable, Bolt, v0, Replit, or Cursor, assume the front end contains at least one Supabase or API URL until you prove otherwise. That is not always a breach: some keys are designed to be visible. The failure mode is treating every string in `.env` as equally safe, or copying a service role key because the assistant said it would "fix auth". Row level security on Supabase is the companion topic; see [Lovable Supabase row level security](/blog/lovable-supabase-row-level-security) before you open signup to strangers.

<ol class="blog-steps">
  <li data-step="1"><h3>Search the repo and the built bundle</h3><p>Grep for key, secret, token, service_role, sk-, and your provider names. Open the production JavaScript in devtools Sources and search again.</p></li>
  <li data-step="2"><h3>Classify each string</h3><p>Publishable by design (Stripe publishable key, Supabase anon key) versus must never be client-side (service role, OpenAI, webhook signing secrets).</p></li>
  <li data-step="3"><h3>Rotate anything that was exposed</h3><p>Treat keys that ever sat in the front end or in a public repo as burned. Issue new keys in the dashboard, then redeploy.</p></li>
  <li data-step="4"><h3>Move privileged calls behind your backend</h3><p>Server routes, edge functions, or a small API you control should hold the sensitive key and enforce who may call what.</p></li>
</ol>

## What the browser may see without panic

Payment providers distinguish publishable and secret keys. The publishable key is expected in checkout UI. Supabase’s anon key is also meant for client apps: the database is supposed to refuse rows that policies do not allow. Security lives in policies and server-side checks, not in hiding the anon string.

Frameworks make the boundary obvious once you know the rule. Vite ships any variable whose name starts with VITE_. Next.js does the same for NEXT_PUBLIC_. If you paste an OpenAI key into such a variable, every visitor can extract it from the minified file. AI assistants sometimes suggest that pattern because it "works" in a demo.

## What must never sit in front-end code

The Supabase service role key is the common accident in generated stacks. It disables RLS for whoever holds it. The same applies to admin tokens, raw database URLs with passwords, signing secrets for webhooks, and any key billed per token use.

Storing secrets only in `.env` on your laptop is not enough if that file is committed, shared in a screenshot, or copied into the hosting UI as a "public" variable. CI logs and error reports also leak values when code logs the full request. Assume the bundle is public; design accordingly.

## A made-up example: the demo that went to Product Hunt

A made-up example: a founder in Bern ships a Lovable app with Google sign-in and a shared task board. The export lists `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` in the readme, which is normal. A second line in the same file is labelled `VITE_SUPABASE_SERVICE_KEY` because the tool once needed to seed data. Nobody removed it before the marketing push. A visitor opens devtools, copies the service key, and lists every row in `profiles` without logging in. The founder rotates the service role in Supabase, moves seeding to a one-off script on a laptop, and adds a server function for any future admin task. The anon key stays in the client; new RLS policies are tested with a logged-out browser session, not only while signed in as themselves.

That sequence fixes the immediate leak. It does not prove the app is ready for regulated data or a security questionnaire.

## What a key audit does and does not prove

Finding no service role in the bundle proves you removed one class of mistake. It does not prove RLS is correct, that API routes check the caller, or that uploaded files are private. Public CVEs around Lovable and Supabase are often about policy gaps, not about stealing a hidden anon key.

Automated scanners help; they miss custom variable names and business logic. Pair grep with one manual session: log out, open the network tab, and try another user’s record ID in the URL or API call. That behaviour is closer to what [is your vibe-coded app production ready](/blog/is-your-vibe-coded-app-production-ready) asks about authorization than any secret search alone.

<div class="blog-faq">
  <h3>Is the Supabase anon key a secret?</h3>
  <p>No. It is publishable by design. Protection comes from row level security and server-side logic, not from hiding the string.</p>
</div>

<div class="blog-faq">
  <h3>Is it enough to keep secrets in .env?</h3>
  <p>Only if that file never lands in the repo, in a client build, or as a "public" variable on your host. Anything named VITE_ or NEXT_PUBLIC_ gets compiled into the bundle.</p>
</div>
