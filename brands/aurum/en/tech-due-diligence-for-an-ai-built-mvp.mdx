## Tech due diligence for an AI-built MVP

**Tech due diligence for an AI-built MVP** is the structured pass an investor, acquirer, or corporate innovation lead runs on your product before they trust it with capital, a pilot contract, or a board slot. They are not asking whether the demo looks clever. They want to know who owns the code, whether strangers can read each other’s data, what breaks at modest load, and how you would fix a security issue without guessing. An app born in Lovable, Bolt, v0, Replit, Cursor, or Claude Code can pass that pass, but only if you treat the export like software, not like a slide deck with a login.

This article is for founders and innovation leads in Switzerland who already have users or a term sheet in sight, and for anyone preparing answers before an external reviewer opens the repository. It is not legal advice on investment documents, and it does not replace a full penetration test when the buyer insists on one.

<div class="blog-pair">

      <li>A round, grant, or acquisition process names a technical reviewer</li>

## What reviewers actually open

Technical diligence on a young product usually spans four buckets. Commercial diligence (market size, churn, unit economics) runs in parallel; do not confuse the two.

<dl class="blog-terms">
  <div>
    <dt>Ownership and IP</dt>
    <dd>Who holds copyright, which contractors signed assignments, and whether employer rules apply to code written by staff.</dd>
  </div>
  <div>
    <dt>Architecture and dependencies</dt>
    <dd>How the front end, API, database, and third-party AI calls connect, and what happens if a vendor changes pricing or terms.</dd>
  </div>
  <div>
    <dt>Security and privacy</dt>
    <dd>Authentication, authorisation, secrets handling, logging, backups, and where personal data are stored.</dd>
  </div>
  <div>
    <dt>Operability</dt>
    <dd>Deployments, monitoring, incident response, and whether one person is the only one who can ship a fix.</dd>
  </div>
</dl>

Ideas as such are not protectable under Swiss law; the implementation is. If an external author wrote components, copyright stays with the author until a written assignment says otherwise. Software created by employees in the course of work belongs to the employer ([Art. 17 URG](https://www.rentschpartner.ch/ict-law/schutz-von-software)). Your data room should show Git history, dependency licences, and contracts, not a slide that says «we own everything».

AI-assisted builds add predictable friction. Generated row-level rules may look green in a dashboard yet fail when the public client key calls the API directly, the pattern behind [CVE-2025-48757](https://nvd.nist.gov/vuln/detail/CVE-2025-48757) on Lovable-linked Supabase projects. Secrets copied into the client bundle, admin routes without server checks, and «works on my machine» deploy scripts are common. None of that means the tool was wrong for validation; it means diligence will ask for proof, not promises.

For load, monitoring, and deploy discipline before you invite scrutiny, use [is your vibe-coded app production-ready](/blog/is-your-vibe-coded-app-production-ready) as a self-check. Diligence goes deeper, but those six questions surface gaps investors notice early.

## How to prepare the repository (founder view)

You do not need a perfect system. You need an honest map and fixes for anything that would embarrass you in a shared screen share.

<ol class="blog-steps">
  <li data-step="1"><h3>Freeze a review branch</h3><p>Tag the commit that matches production. Note the hosting region (for example Supabase eu-central-2 in Zurich) and every subprocessor that touches personal data.</p></li>
  <li data-step="2"><h3>Document the runtime story</h3><p>One page: how a user signs up, which services run on each click, where files land, and which environment variables exist. If you cannot draw it, reviewers will assume the worst.</p></li>
  <li data-step="3"><h3>Prove access control</h3><p>Two test accounts. Attempt cross-tenant reads on every ID-in-the-URL pattern. UI hiding is not evidence.</p></li>
  <li data-step="4"><h3>Scan for secrets and licence risk</h3><p>Search built client assets and the repo for keys. Run the dependency audit on the lockfile you deploy, not an old laptop copy.</p></li>
  <li data-step="5"><h3>State known gaps openly</h3><p>A short table of open risks beats silence. Reviewers punish surprises, not a backlog with owners and dates.</p></li>
  <li data-step="6"><h3>Rehearse the demo under stress</h3><p>Show signup, core value, and logout on a clean browser. Have a rollback story if deploy fails mid-meeting.</p></li>
</ol>

## A made-up example: seed round with a Cursor and Supabase stack

A made-up example: a two-founder B2B SaaS in Zug, not a client. They validated pricing with fifteen pilot users on an app scaffolded in Cursor with Supabase auth and Postgres. A Swiss angel syndicate asks for technical diligence before wiring.

The founders tag `v0.9.4-prod`, write the runtime diagram, and run two-account tests. They find that an edge function returns any project row when the UUID is guessed; they patch policy rules before the reviewer call. They list CVE-related RLS patterns they tested explicitly, rotate an old anon key still present in a commented line, and note «restore untested» on backups. The external reviewer spends a day on repo access, a recorded architecture walkthrough, and a short written follow-up. Findings are mostly operability (no staging environment, one founder holds production keys) rather than «throw the codebase away». The round closes with a condition to add monitoring and shared deploy access within ninety days.

The example is invented. Real timelines and checklists vary by firm. The point is preparation turned a would-be red flag into a scoped remediation plan.

## What a structured security review adds

When diligence is imminent, or when a pilot customer asks for evidence mapped to a published standard, a focused review beats another internal evening with a checklist. Aurum’s [Vibe Code Review](/services/vibe-code-review) targets apps built with Cursor, Lovable, v0, or Claude Code. Work is mapped to OWASP ASVS v5.0. You receive a gap report, roughly eight hours on architecture and code quality, a prioritised P0/P1/P2 action list, a closing conversation, and an NDA.

Book when access control, data location, or code ownership questions are blocking revenue, investment, or a partnership, and you intend to keep the current repository. Use the [contact page](/contact) to describe timing, who will join the closing conversation, and what the other side already requested. Skip the review if you are still proving demand with disposable fake data, if you only need another feature from the AI tool, or if you already committed to a full rewrite and will not ship this codebase to paying users. A review documents gaps; it does not replace your obligation to fix P0 items before you widen access.
